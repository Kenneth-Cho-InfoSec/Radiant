# Android port audit

Audit date: 2026-11-07  
Upstream: `https://github.com/Ka1-S/LYNX-SHARE`  
Audited revision: `ab256f09fdb4fd4130235b20b4841331f0a56602`  
Working branch: `radiant/android-port` (remote `upstream` points to the original repository)

This audit includes the Android native core, the JNI/Compose/JUCE host, and an installable debug APK. API 36 phone launch, compact workspace, `.radiant` serialization, SAF save/open/resave, and API 29 app launch plus host/lifecycle instrumentation have been exercised. API 29 and API 36 SAF CreateDocument/OpenDocument round trips for both `.lynx` and `.radiant`, microphone permission/service arm-disarm, and background playback service tests also pass. The QEMU tablet AVD was tested at expanded landscape, portrait, and 640 dp resizable widths. A Samsung SM-X218U (Android 16/API 36, ARM64) also passed physical launch/lifecycle instrumentation, layout/touch smoke checks, and a short speaker-output check. Medium navigation uses the full editor width; at 640x400 dp the editor area is vertically short. Android 17/API 37 background-audio behavior still needs runtime validation; detailed physical audio performance and broader device coverage remain outstanding.

## Findings

| Area | Source evidence | Android assessment |
|---|---|---|
| C++ core | Root `CMakeLists.txt` declares `lynx_core` as a static C++20 target, separate from JUCE. It includes `src/core` and `src/flp`, plus PocketPy, Monocypher, LAME, WavPack, and libogg/libvorbis targets. | `lynx_core` compiled for Android API 29 on `arm64-v8a` and `x86_64`. Android's x86_64 binary128 `long double` exposed x87 selection guards; those paths now use existing portable fallbacks unless the target has 80-bit extended `long double`. |
| Existing core tests | `lynx_tests` is a CMake executable from `tests/tests.cpp`; it exercises FLP parsing, sequencing, snapshots, instruments, sample handling, mixer, effects, automation, and project behavior. | The ARM64 and x86_64 test executables build. The full x86_64 suite ran on the API 36 emulator: 1,938,851 checks, 0 failures. Tests requiring a supplied FL Studio installation folder use their documented skip path. |
| JUCE and entry point | CMake FetchContent pins JUCE 8.0.4. `src/Main.cpp` defines `LynxApplication : juce::JUCEApplication`; desktop app target uses `juce_add_gui_app`. | The Android target builds JUCE into one `libradiant.so`. The custom Activity initializes JUCE and embeds its peer under a Compose-owned `ViewGroup`. API 36 phone/tablet instrumentation covers resize, orientation and Activity recreation. Tablet widths below 840 dp select one editor with bottom navigation; expanded 1280 dp uses a rail and restores multiple panes. |
| DAW panel hierarchy | `MainComponent` owns Playlist, Channel Rack, Piano Roll, Mixer, and Browser. `Workspace` presents these as floating, resizable, maximizable, detachable panels and persists layout state. | Musical panel model and editor code are valuable reuse candidates. Desktop floating-window behavior needs a single-window compact arrangement on phones; tablet layout can retain multiple panels. |
| Sequencer, mixer, instruments, effects | `lynx_core` includes scheduler, rack renderer, mixer operations, effect and instrument engines, automation, note tools, and workspace operations. | Preserve these sources and test their Android build. Platform SIMD and floating-point flags need review against ARM64 results. |
| Audio device and callback | `AudioEngine` uses JUCE `AudioDeviceManager` and `audioDeviceIOCallbackWithContext`; callback code processes the passed sample count and contains platform-specific thread-priority branches. | Start with JUCE's Android backend. Audit callback allocations/locks and Android thread behavior, then measure on hardware. Existing code is not yet declared real-time safe on Android. |
| Threading | `SnapshotExchange` publishes immutable snapshots with atomics; `WorkerPool` uses Win32, libdispatch, or POSIX semaphores. | POSIX semaphore branch is a plausible Android path, not yet compiled. Thread counts, wake latency, and callback hand-off need device validation. |
| Project serialization | `ProjectFile` serializes version 1 JSON (`format: lynx-project`) to `.lynx`, writing through a temporary file before replacement. | `.lynx` and `.radiant` route through the same serializer. SAF documents stage in app-private files for native random access. API 36 picker save, reopen, and resave passed manually; provider failure and revoked-grant recovery still need tests. |
| FL Studio import | `src/core/FlpImport.cpp` and `src/flp/Flp.cpp` are included in `lynx_core`. Import can resolve user-installed FL data and external DLLs. | Binary parsing and conversions are core candidates. User-owned factory assets and desktop DLLs are unavailable by default on Android; retain unresolved paths/state and report missing assets. |
| Plugin hosting | Desktop `PluginHost` registers desktop formats; CMake enables VST3 and platform-specific VST2/CLAP/LV2 paths. Separate-process sandbox code uses desktop process/shared-memory facilities. | Desktop plugin binaries and sandbox are not an Android plugin strategy. Keep original format IDs, routing, automation references, and state; show a non-destructive placeholder when unavailable. Built-in instruments/effects remain the priority. |
| Platform/filesystem layer | `src/platform/Paths.cpp` selects Windows, macOS, or Linux paths. `ProjectPackage`, `SampleLibrary`, and file choosers use `juce::File`. | Android settings/cache use app-private storage. Kotlin SAF callbacks stream project files to/from staged local files. Sample-folder SAF integration and broad package/import coverage remain outstanding. |
| Desktop-only dependencies | The desktop target includes ASIO, PipeWire, Linux realtime helpers, plugin sandbox/worker processes, native editor embedding, updater, and desktop window ownership. | Exclude or guard desktop drivers and process/window adapters in the Android target. Their functionality must be replaced or explicitly represented as unsupported, not silently linked. |
| Third-party code | Core target vendors PocketPy (MIT), Monocypher (BSD-2/CC0), LAME (LGPL), WavPack (BSD), libogg/libvorbis, and other source/header assets. ONNX Runtime is represented by headers and loaded at runtime in desktop paths. | Audit every shipped resource and license. ONNX ARM64 Android runtime availability is not established. Do not package a desktop binary or claim speech features until a suitable runtime is built and tested. |
| Licensing | Root `LICENSE` is GNU AGPL-3.0. JUCE is offered under AGPLv3 or commercial terms. | Preserve notices and provide corresponding source when conveying an AGPL build. The app must not imply endorsement by LYNX maintainers. Complete a per-resource license audit before release. |

## Compatibility classification (build evidence added 2026-11-07)

1. **Compiled for Android ARM64 and x86_64:** `lynx_core` and its in-tree C/C++ dependencies. A small set of x87-sensitive files now guards the exact 80-bit format rather than CPU family alone; Android x86_64 uses the existing portable implementations.
2. **Android adapters required:** application storage, settings/cache directories, document import/export, audio lifecycle/focus, Activity/native view lifecycle, notifications, and app theme transfer.
3. **Conditional compilation required:** ASIO, PipeWire/JACK/ALSA, Linux realtime policy, desktop plugin formats, process sandbox, native editor embedding, package/update code, and desktop window management.
4. **Dependency verification required:** Android ABI and license support for each bundled codec/crypto/runtime; JUCE 8.0.4 Android exporter behavior; any model or binary assets loaded at runtime.
5. **Desktop-only:** ASIO and the LYNX ASIO driver, PipeWire client, X11/Win32/macOS editor embedding, desktop installers, and separate-process plugin workers.
6. **Substantial redesign:** compact workspace layout, Compose/JUCE host integration, Android storage abstraction, foreground audio service/lifecycle, and touch gesture arbitration.
7. **Licensing:** AGPL-3.0 upstream; JUCE has AGPL/commercial licensing; third-party licenses and media assets require an inventory.
8. **Major risks:** large UI surface (the current entry file is about 10k lines), storage semantics, CPU/memory/thermal load on phones, plugin incompatibility, JNI/JUCE lifecycle ownership, and lack of physical-device audio measurements.

## Remaining proof

Run Android 17/API 37 background-audio validation, more complete Piano Roll/Playlist/Mixer editing and export workflows, interruption/audio-focus tests, recording on physical hardware, SAF revoked-permission and interrupted-write cases, detailed/sustained physical audio measurements, and testing on additional ARM64 devices. The successful Samsung SM-X218U run establishes one physical ARM64 runtime; the x86_64 emulator itself does not validate ARM64 runtime behavior.
